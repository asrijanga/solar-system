# SS-27 · One repository, served from the owner's NAS

Status: **planned** (owner, 2026-10-14: "I will pause this here, I want to move to a single repo and host it via my NAS"). Nothing below is built yet. Each story gets its spec approved before code, as always.

As the owner, I want the whole project in one repository and the site served from my NAS, so that no hosting limit decides how much of each world is shown, and nothing depends on three GitHub Pages sites staying up.

## Where things stand (2026-10-14)

**Three repositories, three Pages sites:**

| Repository | What it holds | What its Pages site serves | Size |
| --- | --- | --- | --- |
| `asrijanga/solar-system` | Everything: app, pipelines, tools, data manifests, docs, baselines | The app, every world's data, and the Moon's terrain (`terrain/`, 671 MB, built by CI's `pipeline:tiles`) | about 0.75 GB |
| `asrijanga/solar-system-mars-data` | Only `.github/workflows/pages.yml`, `README.md`, `SOURCE` (6 commits; head `b08d592`) | Mars's terrain, levels 0–7, built from the app at `SOURCE` | 494 MB |
| `asrijanga/solar-system-mercury-data` | Only the same three files (1 commit; head `e226808`) | Mercury's terrain, levels 0–7, built from the app at `SOURCE` | 489 MB |

**No tiles are in git anywhere.** Every tile set is rebuilt from pinned, checksummed sources by a workflow. The two data repositories exist only because GitHub Pages allows about 1 GB per site. Their workflows and READMEs are already kept in the app repository, in `tools/terrain/mars-data/` and `tools/terrain/mercury-data/`.

**Why moving helps:**
- **Size:** the website's terrain alone is 1.65 GB, which no single Pages site can hold.
- **Flakiness:** cross-site tile fetches have failed captures and one deploy with intermittent 503s and missing CORS headers. PR #62 added retries, which masks the problem rather than removing it.
- **Finer data:** local mode (`npm run local`) already serves every world at full measured detail. It needs a machine with disk and a network, which the NAS is.

**What the app already makes easy:**
- **Relative paths:** the app finds its data by relative URL (`vite.config.ts` `base: './'`, `src/site.ts` `siteUrl`), so it runs under any path on any host.
- **Gzip either way:** the terrain loader recognises gzip by its magic bytes (`src/scenes/tileFetch.ts`), so a server may send tiles as raw `.gz` bytes or with `Content-Encoding`; both work.
- **One build:** everything is static files. Serving it needs a web server, not an application server.

**What the NAS must provide:**
- **HTTPS.** WebGPU runs only in a secure context. `http://nas.local/` will refuse to render, except on the NAS itself as `localhost`. The iPhone needs a certificate it trusts.
- **Disk:**
  - about 2 GB for the site;
  - for building, the pinned sources: Moon about 5.2 GB, Mercury about 1.2 GB, Mars's albedo 978 MB. Mars's HRSC strips (about 35 GB) are streamed, so only its composite (about 2 GB) is kept.
  - local mode's on-demand caches grow with what is viewed, to tens of GB.
- **Memory:** about 4 GB free while building tiles (Mercury's composite holds a 23,040 × 11,520 grid in memory).

## The stories, in order

The order matters. The repositories cannot become one until something other than GitHub Pages can hold all the tiles. So the NAS comes up first, serving a copy of today's site, and the merge comes after.

### N1 · Decisions (owner)

Before any code, the owner decides:

1. **How the site is reached.**
   - **(a) Private, through Tailscale** (recommended). `tailscale cert` or `tailscale serve` gives the NAS a trusted HTTPS name, which the iPhone opens through the Tailscale app. Nothing is exposed to the internet. This also closes SS-7, the private link.
   - **(b) Public, on a domain the owner holds.** Caddy gets a Let's Encrypt certificate itself, with port 443 forwarded on the router. Anyone can visit.
   - **(c) Home network only,** with a self-signed certificate. That certificate must be installed and trusted on every device, the iPhone included, which is awkward.
2. **Where the code lives.**
   - **(a) GitHub stays the code host** (recommended): pull requests, CI and Claude's cloud sessions work as now, and only the hosting moves.
   - **(b) Code moves to the NAS too** (Gitea or Forgejo). Claude's sessions would then need access to that server: the environment's network rules and a token in its secrets.
3. **How the NAS gets each build.**
   - **(a) A self-hosted GitHub Actions runner on the NAS** (recommended). CI builds the site and the tiles where the disk is, keeps the source caches between runs, and copies the result into the served folder.
   - **(b) GitHub-hosted CI builds, and the NAS pulls the result:** a release artifact, or `rsync` over Tailscale.
   - **(c) A timer on the NAS** runs `git pull && npm run build:site`. This is the simplest, but has no review step.
4. **Whether GitHub Pages stays as a public mirror** of the app without the heavy terrain, or is switched off.
5. **The NAS itself:** its make and operating system (Synology DSM, QNAP, TrueNAS, Unraid, plain Linux), whether it runs Docker, and how much disk the project may use. Every budget below becomes an owner-set number.

### N2 · The NAS serves today's site, over HTTPS

As the owner, I want the NAS to serve exactly what GitHub Pages serves now, so that hosting is proven before anything else changes.

**Steps:**
- A Caddy container (or the NAS's own web server) serves one folder, with the certificate chosen in N1.
- **Content types:** `.terrain` as `application/octet-stream`, plus `.webp`, `.json` and `.bin`. If the server compresses responses, it must not compress the already-gzipped `.terrain` files again.
- **Caching:** tiles carry no content hash in their names, so each build's folder is swapped in atomically (a symlink switch), and responses get `ETag`s.
- **First copy:**
  - the app's built site, the same as the Pages artifact;
  - the Moon's `terrain/`;
  - the two data sites' `terrain/` folders.
  - These are downloaded once, or rebuilt with the existing scripts.

**Acceptance:**
- The NAS URL opens `/moon/`, `/mars/` and `/mercury/` on the iPhone, with terrain.
- `npm run capture` passes against a build whose terrain addresses point at the NAS.
- Nothing in the repository changes yet.

### N3 · Builds go to the NAS

As the owner, I want every merge to main to update the NAS, so that shipping stays routine.

**Steps:**
- **The pipeline** chosen in N1 (3a, 3b or 3c).
- **One command, `npm run build:site`, builds the whole served tree:**
  - the app (`npm run build`);
  - the Moon's tiles (`pipeline:tiles`);
  - Mars's (`pipeline:mars:terrain`, then `pipeline:mars:tiles`);
  - Mercury's (`pipeline:mercury:tiles`).
  - It writes them into one folder.
- **Pinned sources** are downloaded once into a persistent cache on the NAS. Every file is re-verified by SHA-256 on use, as now.
- **Reproducibility:** the reproducibility checks of the data repositories' workflows come along unchanged. A rebuilt composite must reproduce the committed manifests and source maps byte for byte.

**Acceptance:**
- A merge to main is live on the NAS within the time the owner sets.
- A failed build leaves the previous site serving.

### N4 · One repository

As the owner, I want the two data repositories folded into the app repository, so that one place holds everything and one origin serves it.

**Folding the repositories in.** Their contents are three small files each, already mirrored in `tools/terrain/*-data/`, so no tiles move.

Their history (6 and 1 commits) is kept with a subtree merge, so `git log` still shows how each site was built:

```sh
# In a clone of asrijanga/solar-system, on a new branch:
git remote add mars-data https://github.com/asrijanga/solar-system-mars-data
git remote add mercury-data https://github.com/asrijanga/solar-system-mercury-data
git fetch mars-data
git fetch mercury-data

# Each repository's history, kept, under its own folder:
git merge -s ours --no-commit --allow-unrelated-histories mars-data/main
git read-tree --prefix=hosting/mars-data/ -u mars-data/main
git commit -m "Fold solar-system-mars-data (6 commits, head b08d592) into hosting/mars-data/"

git merge -s ours --no-commit --allow-unrelated-histories mercury-data/main
git read-tree --prefix=hosting/mercury-data/ -u mercury-data/main
git commit -m "Fold solar-system-mercury-data (1 commit, head e226808) into hosting/mercury-data/"

git remote remove mars-data
git remote remove mercury-data
```

`git subtree add --prefix=hosting/mars-data mars-data main` does the same in one step where `git subtree` is installed.

**Simpler alternative:** history matters little here, since every commit's content is already in the app repository, and the story records both heads. The folders can simply be copied in with their head SHAs in the commit message.

**After the fold:**
- **One copy of each file:** `hosting/*-data/pages.yml` and `tools/terrain/*-data/` are duplicates. Keep one: their build steps move into N3's `build:site`, and the old workflows are deleted.
- **One origin for all terrain:**
  - `MARS_TERRAIN_SITE` (`src/scenes/marsSite.ts`) and `MERCURY_TERRAIN_SITE` (`src/scenes/mercurySite.ts`) become same-origin relative paths through `siteUrl`, as the Moon's already is.
  - Proposed layout: `terrain/moon/`, `terrain/mars/` and `terrain/mercury/` (the Moon's moves from `terrain/`).
  - Local mode's own folders (`/mars-terrain/` and the others, levels 8 and up) are kept separate from these.
- **Captures and allocation stop fetching across sites:**
  - `tools/capture/run.ts` and `tools/perf/alloc.ts` drop their routes to the data sites. The harness serves the built tiles locally, as it already does the Moon's.
  - This removes the network from every capture (CLAUDE.md, "Captures do not depend on the machine"). The retries of PR #62 go with it.
- **CI:** the captures job needs the Mars and Mercury tiles, as it has the Moon's. They are built once, then restored from the Actions cache, keyed on the build code. On a NAS runner (N1 3a) the cache is just a folder.
- **Budgets:**
  - The 950 MB per-site limits in `tools/terrain/mars.ts` and `tools/terrain/mercury.ts`, and the Moon's, become one disk budget for the whole tree, set by the owner in N1.
  - The size checks stay; only their number changes, with the owner's approval stated in the PR (CLAUDE.md, "Never tune a check to pass").
- **Docs:**
  - CLAUDE.md: the Pages references and the commands.
  - `docs/world-recipe.md` W4: "When a world's detail outgrows its share of the 1 GB, its tiles move to a data repository of its own" becomes "its tiles go in the one served tree, within the owner's disk budget".
  - README: the "Storage" paragraph.
  - Each world's story: where its terrain is.

**Acceptance:**
- Every capture matches its baseline with no network access at all. The baselines must not change: the same tiles, from a different address.
- `npm run check`, `npm run alloc` and the pipeline job pass.
- The NAS serves the result of `build:site`.

### N5 · Retire the old sites

As the owner, I want the old sites switched off once the NAS has served for a while, so that nothing stale is left public.

**Steps:**
- **The data repositories:**
  - turn off GitHub Pages in each one (Settings → Pages);
  - then archive them (Settings → Archive this repository). Archiving keeps them readable and links still resolve.
- **The app's Pages site:** turn it off, or keep it as the public mirror the owner chose in N1 (the app without terrain beyond the Moon's 1 GB).
- **Links:** the README's live links and the home page point to the NAS address.
- **Workflows:** remove the `pages.yml` deploy, or keep it for the mirror.

**Acceptance:** nothing in the repository refers to `solar-system-mars-data` or `solar-system-mercury-data`, except history and this story.

### N6 · Full detail by default (optional, later)

As a learner, I want the NAS to show every world at full measured detail, so that the website and local mode are one thing.

**What it is:**
- `npm run local` (SS-10c, SS-14 W5) already builds tiles finer than level 7 on demand, from PDS and JAXA files.
- On the NAS it can run as a service behind Caddy. The site then streams levels 0–7 from the built tree, and finer levels on demand: for the Moon down to Kaguya's 8 m, and for Mars to HiRISE.

**Owner decisions:**
- the disk the on-demand cache may grow to;
- whether the labelled approximation below the measurements (SS-10b, local mode only) stays off by default. It must, by CLAUDE.md, unless the owner decides otherwise.

**Acceptance:** the local-mode checks (registration, fall-through, no invented values) run against the service as they do against `npm run local`.
